# ADR 0005: テスト戦略 — 単体テストで数式を固定し、数値一致検証はローカルツールに留める

## Status

Accepted

## Context

前処理・デコードには、YOLOX 公式実装に合わせた壊れやすい仕様がある (BGR のまま扱う、パディングは右下のみ、grid 順序は stride 昇順で y 外側 / x 内側)。これらは崩れてもビルドは通り、精度だけが静かに落ちるため、コメントだけでは守れない。

一方、仕様が Python 実装と一致しているかは実モデル・実画像がないと確認できない。モデルを CI のたびにダウンロードすると CI の成否がネットワークに左右され、Python 環境の追加は gcc/clang マトリクスの実行時間と保守対象を増やす。

## Decision

テストを役割で 2 層に分ける。

1. **単体テスト (GoogleTest)**: 手で組んだ合成データで、grid/stride 生成順・デコード式・スコア閾値の境界・座標逆変換とクリップなど **数式そのもの** をピン留めする。モデルファイルを使わないので **CI で常に実行する回帰ゲート** とする
2. **数値一致検証 (`scripts/verify_parity.py`)**: letterbox・decode・NMS を numpy で独立に再実装し、実モデル・実画像に対する C++ CLI の標準出力と突き合わせる。**CI には組み込まない** 開発者向けツールとし、結果はコミットメッセージや PR 説明に記録する

比較には C++ CLI のテキスト出力 (`class= score= x= y= w= h=` 行) をパースして使う。中間ダンプ機能や Python バインディングは作らない。実装を共有するより、独立した 2 実装が最終出力で一致するほうが検証として強いため。

## Consequences

- CI は GoogleTest のみを実行し、Python 環境やモデルのダウンロードに依存しない
- ⚠️ parity 検証は手動実行なので、怠っても気づきにくい。継続的な保証ではなく、仕様の一次的な裏付けに留まる。定期実行に格上げするには自己ホストランナーなどが要る
- `std::cout` の既定精度 (有効数字 6 桁) のため座標は完全一致しない。`--atol` (既定 0.05px) はこの丸めを吸収する。BGR/RGB の取り違えのような仕様のズレは数十〜数百 px の誤差として現れるため、この許容幅でも検出できる

# ADR 0005: テスト戦略 — 単体テストで数式を固定し、数値一致検証はローカルツールに留める

## Context

Phase 2 で letterbox・decode・NMS の実装は完成したが、Phase 3 開始時点で単体テストがあるのは letterbox と NMS のみで、grid/stride デコード (`src/postprocess/decode.cpp`) が未検証だった。CLAUDE.md に記録した「BGR のまま RGB 変換しない」「パディングは右下のみ」「grid 順序は stride 昇順・y 外側/x 内側」という 3 仕様は、Phase 2 で試行錯誤の末に到達したものであり、コメントとして書かれているだけでは、将来のリファクタリングで静かに崩れても誰も気づけない。

一方で、これら 3 仕様が実際に Python (PyTorch/ONNX Runtime) 実装と一致しているかどうかは、実モデル・実画像を使わないと確認できない。実モデルは 3〜6MB の ONNX ファイルであり、CI 実行のたびにダウンロードさせるとネットワーク状況に CI の成否が左右される。また Python 環境 (numpy / onnxruntime / opencv-python) を CI ジョブに追加すると、C++ ビルドマトリックス (gcc/clang) の実行時間・保守対象が増える。

## Decision

テストを役割で 2 層に分ける。

1. **単体テスト (GoogleTest, `tests/test_decode.cpp` ほか)**: 合成データ (手で組んだ小さな入力配列) を使い、grid/stride 生成の順序・デコード式・スコア閾値の境界・座標逆変換とクリップといった **数式そのもの** をピン留めする。モデルファイルを一切使わないため CI で無条件に実行できる。回帰ゲートとして機能する
2. **数値一致検証 (`scripts/verify_parity.py`)**: letterbox・decode・NMS を numpy で独立に再実装し、実モデル・実画像に対する C++ CLI の標準出力と突き合わせる。これは「仕様が Python 実装と食い違っていないか」を一次的に裏付けるための開発者向けツールであり、CI には組み込まない。実行はローカル開発者の判断に委ね、結果はコミットメッセージや PR 説明に記録する運用とする

比較面は C++ 側の標準出力 (`class= score= x= y= w= h=` 行) のパースとし、C++ CLI にデバッグ用の中間ダンプ機能は追加しない。C++ を Python から直接呼び出すバインディングも作らない — 2 つの独立した実装が最終出力で一致することの方が、実装を共有してしまうより検証として意味がある。

## Consequences

- CI (`.github/workflows/ci.yml`) は GoogleTest のみを実行すればよく、Python 環境やモデルダウンロードに依存しない。gcc/clang 双方で高速に完走する
- parity 検証はネットワーク (モデル DL) と Python 依存 (`scripts/requirements-dev.txt`) を要するため、実行を怠っても気づきにくい。実質的に「壊れていないことの継続的な保証」ではなく「一度きりの仕様裏付け」に留まる。将来的に自己ホストランナー等で定期実行に格上げする余地は残す
- `std::cout` の既定精度 (有効数字 6 桁) により座標は完全一致しない。`verify_parity.py` の許容誤差 (`--atol`、既定 0.05px) はこの丸めを吸収するためのものであり、仕様レベルのズレ (例: BGR/RGB 取り違え) は数十〜数百 px 規模の誤差として現れるため、この許容幅でも検出力は十分
